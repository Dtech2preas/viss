## 1. EXECUTIVE SUMMARY
"Together Forever" is a highly personalized, closed-ecosystem application built strictly for a couple, Jonas and Owami. Its primary function is to maintain constant background synchronization of location, mood, activities, and study habits, alongside offering interactive mini-games and relationship milestones.

The platform prioritizes absolute reliability, guaranteed background execution, and immediate state reflection over battery optimization or standard design constraints. It utilizes a hybrid approach: a web-based Single Page Application (SPA) driven by vanilla JavaScript, deeply embedded within a custom Android wrapper (`WebView`) that supercharges the web app with native OS privileges (like persistent Foreground Services, Biometrics, and Exact Alarms).

---

## 2. SYSTEM ARCHITECTURE & INFRASTRUCTURE
The architecture is divided into three highly interdependent pillars:
1.  **Frontend (Web/UI Layer):** Served from `together.preasx24.co.za`. Built purely with HTML, CSS, and Vanilla JavaScript. It uses `localStorage` for session management and relies on `auth-check.js` to enforce security.
2.  **Backend Data & Logic (Cloudflare Workers + KV):** A serverless `worker.js` script acts as the primary REST API. It handles authentication and merges deep JSON state payloads into Cloudflare KV storage. It uses a dual-versioning system (`/api/couple/check`) to minimize payload bandwidth.
3.  **Real-time Engine & Background OS (Firebase + Android):**
    *   **Firebase Realtime Database:** Handles ultra-low latency, high-frequency data streams—specifically live GPS locations, device stats, and instant background polling triggers (`forceUpdate`).
    *   **Android App (`app/`):** A Kotlin-based native wrapper that bypasses Android Doze mode using `AlarmManager.setAlarmClock()` and persistent Foreground Services to ensure continuous background tracking and real-time push notifications.

## 3. STATE MANAGEMENT & DATA SYNCHRONIZATION
The application uses a unique dual-backend state management strategy:

*   **Global App State (Cloudflare KV):**
    *   Stored under a single key: `couple_jonas_owami`.
    *   When the frontend (via `authenticatedFetch`) or the Android background service (via `CoupleService.CLOUD_SYNC`) updates data, it sends a partial JSON payload to the worker.
    *   The worker executes a recursive `mergeDeep()` function, preserving existing fields and updating only the provided keys.
    *   To prevent Cloudflare KV quota exhaustion (1000 PUTs/day), the app uses a versioning system (`couple_jonas_owami_version`). Background services ping the lightweight `/api/couple/check` endpoint first and only download the full payload if the version increments.
    *   *Constraint mitigation:* Heavy payloads like image uploads are aggressively compressed (Canvas base64 resizing) before transmission to avoid KV size limits.

*   **Real-time High-Frequency State (Firebase):**
    *   Managed locally via deterministic SHA-256 generation (`firebase_secret_path`).
    *   Used for the `forceUpdate/<userName>` trigger, `locations/`, and `history/` nodes.
    *   Allows the frontend (`location.html`) and backend (`CoupleService`) to react instantly without expensive HTTP polling.

## 4. SECURITY & AUTHENTICATION
Security in "Together Forever" relies on strict knowledge-based authentication, hardware biometrics, and dynamic path obfuscation:

*   **Knowledge-Based Auth (`index.html`):** The user must answer four highly specific relationship questions (e.g., Owami, Seakwa, 41, Red and Blue). Answering correctly issues a hardcoded token (`auth_token_jonas_owami_secure_2024`).
*   **Token Persistence & Redirection:** `auth-check.js` runs on every page. If the token is missing from `localStorage`, the user is immediately redirected to `index.html`.
*   **Android Bridge Interception:** When JS sets the profile or token in `localStorage`, the Android `MainActivity` intercepts this via `@JavascriptInterface AndroidBridge` and securely persists it into native `SharedPreferences`.
*   **Hardware Biometrics:** On Android, `MainActivity.kt` enforces `BiometricManager` authentication (fingerprint/face) upon app launch, but *only* after sequentially processing all required system permission prompts and intents (to prevent the biometric prompt from being overridden by system dialogs).
*   **Firebase Deterministic Security:** Firebase is technically open to the public. To secure data, the auth answers (Q1, Q2, Q3) are hashed client-side via SHA-256 to create a `firebase_secret_path`. All sensitive location data is nested under this unguessable hash (e.g., `locations/<secretHash>/jonas`).

## 5. ANDROID NATIVE INTEGRATION (APP MODULE)
The Android application is the engine ensuring 100% guaranteed background execution, prioritizing functionality over battery life.

*   **`CoupleService.kt` (The Core Engine):**
    *   A persistent Android Foreground Service.
    *   Runs a continuous polling loop to check Cloudflare for state changes and Firebase for `forceUpdate` requests.
    *   **Location Tracking:** Polls GPS every 15 minutes routinely, or every 30 seconds during 'Trip Mode'. Evaluates `NetworkCapabilities` (including `TRANSPORT_VPN`) to dynamically shift priority between `PRIORITY_HIGH_ACCURACY` (offline/trip) and `PRIORITY_BALANCED_POWER_ACCURACY` (online/routine).
    *   **Offline Queueing:** If network fails, locations are saved locally (`SharedPreferences`) and batch-uploaded to Firebase `/history` upon reconnection.
    *   **Stationary Detection:** Compares new GPS coordinates against the *last locally uploaded* coordinates to prevent infinite update loops when stationary.
    *   **Notification Engine:** Compares incoming Cloudflare JSON with a cached `lastPartnerState_<name>`. If a change is detected (e.g., mood change, study start, or an unlocked scheduled message), it fires a native push notification.

*   **Alarm & WakeLock Strategy:**
    *   To survive Android 14/15 Doze Mode, the app uses `AlarmManager.setAlarmClock()` combined with `android.permission.USE_EXACT_ALARM`.
    *   Alarms trigger `AlarmReceiver` -> `AlarmActivity` (using `USE_FULL_SCREEN_INTENT`) to wake the screen and play ringtones.
    *   `MediaPlayer` uses `setWakeMode(PowerManager.PARTIAL_WAKE_LOCK)` to prevent CPU sleep during ringtone playback.
    *   App restarts after reboot via `BootReceiver` and survives swipe-to-kill via `onTaskRemoved` scheduling.
    *   *Recent Change:* Permanent WakeLocks were explicitly removed by the user to save some battery; the app now relies purely on robust Foreground Service and AlarmManager design.

*   **Widgets & Logs:**
    *   `TogetherWidgetProvider.kt`: A home screen widget displaying partner mood, distance, and stats.
    *   `AlarmLogger.kt`: Persists up to 2000 diagnostic alarm logs in `SharedPreferences`, accessible via the web UI (`alarm-logs.html`).

## 6. WEB FRONTEND & USER INTERFACE (HTML/JS)
The web layer provides the visual dashboard and interactive elements.

*   **Styling:** Enforced globally by `global-style.css`. Uses 'Montserrat' for body text, 'Dancing Script' for headings, and a signature pink/purple gradient theme (`#ff7eb9` to `#7e57c2`).
*   **State Access:** JS strictly uses lowercase names (`getCurrentUser()`, `getPartnerName()`) to access object keys in state to prevent index mismatches, unlike Cloudflare KV which stores original casing.
*   **Map Visualizations (`location.html`, `location_history.html`):**
    *   Uses Leaflet and AntPath for animated trails.
    *   Implements dynamic OSRM routing: If computed speed between GPS points is >= 10 km/h, paths snap to roads. If < 10 km/h, they use straight lines.
    *   Third-party API calls (Nominatim, Open-Meteo, OSRM) use aggressive Promise-caching to prevent concurrent duplicate requests driven by reactive Firebase listeners.
*   **Debugging UI:** The floating `debug-console.js` is intentionally disabled (empty function stubs) to hide debug info from the UI without breaking script tags globally.

## 7. BACKEND APIs & CLOUDFLARE WORKERS
The `worker.js` script deployed to Cloudflare handles the REST API:
*   **CORS:** Strictly limits cross-origin access to `https://together.preasx24.co.za`.
*   **Authentication Middleware:** Validates the static `Bearer auth_token_...` on all `/api/couple` routes.
*   **Endpoints:**
    *   `POST /api/auth`: Validates answers, writes them to KV if missing, returns token.
    *   `GET /api/couple/check`: Returns current state version integer.
    *   `GET /api/couple`: Returns the full JSON payload.
    *   `POST /api/couple`: Executes the `mergeDeep` algorithm and increments the version integer.
    *   `GET / POST /api/memories`: Handles an isolated array of special memories.

## 8. DATABASE: FIREBASE REALTIME & CLOUDFLARE KV
*   **Cloudflare KV (Long-term State):** Excellent for reads, highly restricted for writes (1000/day limit). Used for moods, points, coupons, game state, and scheduled messages.
*   **Firebase Realtime DB (Live Data):**
    *   **`/forceUpdate/<userName>`**: Located at the ROOT of the DB (unlike locations). Requires explicit security rules. It uses a `{ requestId, timestamp }` object to ensure subsequent identical requests trigger listeners.
    *   **`/locations/<secretHash>/<userName>`**: The partner's most recent live coordinate.
    *   **`/history/<secretHash>/<userName>`**: Appended history nodes used for drawing trails.

## 9. CORE WORKFLOWS & ALGORITHMS

*   **Location Update Flow:**
    1. Partner A clicks "Force Update" on `location.html`.
    2. Writes `{requestId, timestamp}` to Firebase `/forceUpdate/partner_B_Name`.
    3. Partner B's Android `CoupleService` (listening via `ValueEventListener`) detects the change instantly.
    4. Partner B forces high-priority GPS fetch, calculates distance against last upload, pushes new coord to `/locations/<hash>/partner_B`.
    5. Partner A's `location.html` (listening to `/locations`) updates the UI instantly, confirming success by verifying the timestamp increased.

*   **Scheduled Message Flow:**
    1. User A creates a message with an `unlockAt` timestamp.
    2. Payload merges to Cloudflare.
    3. UI explicitly hides messages where `Date.now() < unlockAt`.
    4. Partner B's `CoupleService` polls Cloudflare. It evaluates `unlockAt` against current time.
    5. If unlocked and not previously notified (tracked via `lastNotifiedUnlockedMessagesCount` in `SharedPreferences`), it triggers an Android Notification.

## 10. FILE-BY-FILE COMPREHENSIVE BREAKDOWN

### Web Client Core
*   **`index.html`**: Entry gate. Renders a form with the 4 security questions. Calls `/api/auth`.
*   **`you.html`**: Profile selection dashboard. Sets `togetherProfile` in localStorage and initiates bridge sync to Android.
*   **`auth-check.js`**: Core client security logic. Intercepts fetch calls (appending the API Base URL: `https://shrill-base-9781.dtechxpreas.workers.dev`), redirects unauthenticated users, and generates the `firebase_secret_path` SHA-256 hash.
*   **`global-style.css`**: Global design system enforcing the pink/purple gradient and specific font families.
*   **`worker.js`**: Serverless Cloudflare logic handling deep-merging, versioning, and CORS.
*   **`custom-alerts.js`**: Custom UI overlays replacing native `window.alert`/`confirm` to maintain aesthetic immersion.
*   **`debug-console.js`**: Intentionally neutered debug script to globally disable on-screen developer logs.

### Dashboards & Trackers
*   **`location.html`**: Live map dashboard. Fetches coordinates, reverse-geocodes addresses via Nominatim, fetches Open-Meteo weather, and draws paths. Utilizes Promise-caching for API optimization. Uses strict heuristic (e.g., <2m live, >30m offline) to determine partner status.
*   **`location_history.html`**: Historical map dashboard. Polls Firebase `/history`, calculates velocity between nodes to determine if OSRM road-snapping (driving) or straight lines (walking) should be used via Leaflet AntPath.
*   **`life-dashboard.html` / `life-stats.html` / `study-dashboard.html`**: Analytical views utilizing `Chart.js` to visualize relationship health, mood frequency, and study hours.
*   **`study.html`**: A Pomodoro timer that synchronizes real-time "focus state" to Cloudflare, triggering "Partner is studying" notifications.
*   **`mood.html`**: Simple UI to select emotional states. Triggers Cloudflare sync and subsequent Android notifications.
*   **`activities.html`**: Allows manual override of current activity state.

### Interactive & Gamification
*   **`coupons.html`**: System to spend relationship points on predefined favors.
*   **`messages.html`**: "Love Notes" system featuring time-locked scheduled messages.
*   **`games.html`, `game.html`, `gameplay.html`**: Hub for interactive multiplayer games.
*   **`tic.html`, `rock.html`, `roulette.html`**: The specific mini-games utilizing Cloudflare KV as a slow-turn multiplayer server.
*   **`bucket.html`**: Shared life goals checklist.
*   **`memories.html`, `mem.html`**: Dedicated UI for appending and viewing long-form memories (stored in the secondary `/api/memories` endpoint).
*   **`milestones.html`**: Hardcoded timeline of critical relationship dates (e.g., Anniv: Sep 21 2024).
*   **`nano.html`**: Specialized anniversary animation page.

### Admin & Debug
*   **`alarm-logs.html`**: Renders `AlarmLogger.kt` JSON data from SharedPreferences via AndroidBridge for remote diagnostic tracking of Doze mode behavior.
*   **`private.html`**: Historically passcode-gated section for sensitive data.

### Android Native Core (`app/src/main/`)
*   **`MainActivity.kt`**: Activity entry. Manages ActivityResultLaunchers to chain permission requests (battery optimization, exact alarms) before finally requesting Biometric auth. Sets up WebView, injects `localStorage` listeners, and defines `@JavascriptInterface AndroidBridge`.
*   **`CoupleService.kt`**: The monolithic Foreground Service. Implements dynamic location polling, offline queuing, Firebase RTDB integration, battery-conscious WakeLock removal, and Notification diffing logic against `ackState`. Uses `checkAndNotify()` against `lastPartnerState_X`.
*   **`AlarmActivity.kt`**: Specialized Activity utilizing `USE_FULL_SCREEN_INTENT` to forcefully wake the device screen and play loud MediaPlayer ringtones, escaping Doze constraints.
*   **`TogetherWidgetProvider.kt`**: BroadcastReceiver powering the Android Home Screen Widget. Reads cached metrics (mood, distance) from `SharedPreferences`.
*   **`AlarmReceiver.kt` / `PollReceiver.kt` / `BootReceiver.kt`**: Critical receivers ensuring `CoupleService` survives swiping-to-kill, reboots, and OS memory reclamation.
*   **`AlarmLogger.kt`**: Utility appending timestamped JSON strings to SharedPreferences regarding service lifecycles and exception catches.
*   **`MyApp.kt`**: Initializes Firebase context instantly upon app process creation.
*   **`AndroidManifest.xml`**: Declares rigorous permissions (`SCHEDULE_EXACT_ALARM`, `USE_EXACT_ALARM`, `RECEIVE_BOOT_COMPLETED`, Location, Camera) and defines service behaviors.

### Build & Config
*   **`build.gradle.kts` (App & Root)**: Defines Kotlin dependencies (OkHttp, Gson, Play Services Location, Biometrics). Configured for API 34.
*   **`worker.js`**: (Cloudflare Backend script).

## 11. BUILD, DEPLOYMENT & TESTING
*   **Deployment Policy**: The user heavily prefers "online" fixes (deploying HTML/JS to Cloudflare/Host) over requiring APK recompilation and re-installation, to minimize friction for the partner.
*   **Testing Strategy**: Uses Playwright via Python (`page.add_init_script` to inject mock `localStorage` tokens and `page.route` to mock backend API calls). Uses `pytesseract` to verify visual text elements in headless screenshots.
*   **CI/CD**: Android APKs are auto-built via GitHub Actions (`.github/workflows/android.yml`). Web assets are hosted remotely on `together.preasx24.co.za`.
